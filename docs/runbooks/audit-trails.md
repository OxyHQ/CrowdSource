# Reading the audit trails

**There are two, they are different PostgreSQL tables, and neither contains the
other's rows.** Reaching for the wrong one is how an investigation concludes
that nothing happened.

| | `audit_events` | `staff_audit_events` |
| --- | --- | --- |
| Scope | **Tenant** — every row belongs to one application | **Unscoped** — staff act across every tenant |
| Records | What an application's credentials and its own team did | What an Oxy operator did |
| Read by | The tenant, at `GET /v1/console/applications/{id}/audit` | Nobody, over HTTP. Query the database. |
| Defined in | `modules/audit/audit.collection.ts` | `modules/console/staffAudit.collection.ts` |

The split is structural, not tidiness. A staff read spans every tenant at once,
so filing it in a tenant-scoped trail would force a choice between two wrong
answers: pick one tenant and the trail is incomplete, or write a row per tenant
touched and every customer's trail fills with activity generated by somebody
else.

Both are **append-only by construction** — nothing in either module updates or
deletes — and **neither may carry reported material**. Codes, ids and outcomes
only. An audit trail is the longest-retained data in the system, so a field that
occasionally held a fragment of an envelope would keep that fragment long after
the case it belonged to was deleted.

---

## `audit_events` — the tenant trail

### Actions

Ingress and access, which is where the tenant boundary is either held or broken:

| Action | Written when |
| --- | --- |
| `report.ingress.accepted` | A report was stored. In the **same transaction** as the report. |
| `report.ingress.replayed` | A retry returned an existing `reportId`. |
| `report.ingress.rejected` | A delivery was refused. Carries `reason`. |
| `report.receipt.read` | `GET /v1/reports/{id}` hit. |
| `case.read` | `GET /v1/cases/{id}` hit. |
| `decision.read` | `GET /v1/decisions/{id}` hit. |
| `appeal.filed` / `appeal.filed.replayed` | An appeal, as an act and nothing more. |
| `console.credential.issued` | |
| `console.credential.revoked` | |
| `console.webhook.secret.rotated` | |
| `console.delivery.replayed` | |
| `console.application.created` | |

An accepted ingress joins the report's own transaction — an accepted report with
no trail is the gap this collection exists to close. A **rejected** ingress has
no transaction to join, and is recorded anyway.

**Reads are audited on a hit, never on a miss.** A `404` is deliberately
indistinguishable from "belongs to another tenant", so auditing misses would
fill one tenant's trail with rows generated by another tenant's probing.

### The two actor fields, and why they are separate

`actorCredentialId` and `actorOxyUserId` are two nullable fields, never one
polymorphic actor, so a query for one can never accidentally match the other.

> **"The leaked key did it" and "this member of your team did it" are different
> incidents with different responses.**

During a credential incident the question is *which* of an application's
credentials acted, not merely which application — which is why the credential id
is recorded and not just the tenant.

`actorOxyUserId` here is a **console member**: a tenant's own staff acting on the
tenant's own configuration. It is **never a reviewer identity**. A reviewer's Oxy
id is never written next to a case, anywhere.

### Refusal reasons

A closed vocabulary, because a free-text reason is where an envelope fragment
ends up: `schema_invalid`, `application_mismatch`, `unsafe_resource_url`,
`policy_unknown`, `payload_conflict`.

### Queries

Indexed for the two questions an operator actually asks:

```sql
SELECT * FROM audit_events
WHERE application_id = 'app_…'
ORDER BY occurred_at DESC;

SELECT * FROM audit_events
WHERE application_id = 'app_…' AND case_id = 'case_…'
ORDER BY occurred_at DESC;
```

`subjectId` carries the object a console act was about — a credential id, an
endpoint id, a delivery id, an application id. **An id and never a value**: no
secret, no URL, no name.

### What is missing from it

- **Membership changes are not in this trail.** A seat is *organization*-scoped
  and this collection is *application*-scoped, so recording one would mean
  inventing an application for it to belong to. What exists is on the membership
  row — `invitedByOxyUserId`, `status`, `revokedAt` — which is **not
  append-only**: a re-grant overwrites the previous inviter. If you need "who
  granted this seat, and when", the answer may have been overwritten. An
  organization-scoped audit collection is the fix.
- **Step-up authentication is not implemented**, and this trail is what stands in
  for it. Irreversible and export actions are meant to require a second,
  stronger authentication; that needs a capability from Oxy's identity layer, and
  a locally invented one would be a second definition of what authentication
  means here. So the irreversible console actions are **recorded rather than
  gated**, and an `admin` seat is what authorizes them.

## `staff_audit_events` — the privileged trail

Every Trust & Safety route appends one row. All five of them:

| Action | Route |
| --- | --- |
| `staff.applications.read` | `GET /v1/trust-safety/applications` |
| `staff.escalated.read` | `GET /v1/trust-safety/escalated` |
| `staff.metrics.read` | `GET /v1/trust-safety/metrics` |
| `staff.deadletter.read` | `GET /v1/trust-safety/deliveries/dead-letter` |
| `staff.standing.changed` | `POST /v1/trust-safety/applications/{id}/standing` |

A row names the operator, **the roles they held at the time**, and at most one
application id. The roles are copied rather than joined, and that is the field
worth understanding: a trail that read the roster at query time would answer
"what may they do *now*", and the question during an investigation is "what were
they entitled to *then*" — which changes the moment a role is revoked, exactly
when the trail matters most.

**The write is not best-effort.** A staff read that could not be recorded
*fails* rather than proceeding unrecorded. Append-only audit is the only control
against insider abuse, and a surface that quietly serves cross-tenant data when
its audit write fails is a surface with no control at all.

Nothing here may carry case material or a subject's identity. The trail of who
looked at what must not itself become a copy of what they looked at.

### Queries

Indexed for both directions of the investigation:

```sql
-- What did this operator do?
SELECT * FROM staff_audit_events
WHERE actor_oxy_user_id = 'oxy_…'
ORDER BY occurred_at DESC;

-- Who has been looking at this application?
SELECT * FROM staff_audit_events
WHERE application_id = 'app_…'
ORDER BY occurred_at DESC;
```

There is **no HTTP route that reads this trail**, for any caller class.

## What the trails cannot tell you

Say these plainly when someone asks, because the absence is not obvious from a
successful query returning nothing:

- **Who reviewed a case.** By design and permanently. No trail, no console
  route, no aggregation returns a `reviewerId` next to a case. The
  cross-tenant queries return counts; a count cannot name anybody whatever is
  added to it.
- **What a juror voted.** Individual votes never leave the database; a decision
  publishes aggregates only — size, decisive votes, winning votes, agreement.
- **Who reported something.** `reporterFingerprints` exist to be counted, and
  are never served to any caller — they are domain-separated by the
  application's own id over its own principal ids and keyless, so an application
  handed them could recompute them over its user table and de-anonymise its own
  reporters.
- **Which cases relate to the same material across applications.** There is no
  `Incident` collection; `cases.incidentId` is `null` on every document. This
  correlation does not exist.
- **When evidence was accessed.** Media resolves through the shared Oxy chokepoint,
  whose access logging is the platform's, not CrowdSource's. Nothing here records
  a file being viewed.

## Juror data is protected by FIELDS, not by the tenant

The one thing to carry away before adding any query near a review, because it is
counter-intuitive and the intuition is dangerous. `Assignment`, `Review`,
`ReviewerProfile`, `SortitionDraw`, `ReviewerAffinity` and `ReviewerRelation` are
declared through `defineUnscopedCollection` — correctly, since a reviewer belongs
to no tenant and the draw spans every application by design.

**So the tenant filter is not the control here, and there is nothing underneath
it to fall back on.** A module wanting juror identity across every application
needs no allowlist entry and no new primitive: it can read `Review` unfiltered
through the ordinary wrapper today. The named-query control protects `cases` and
`decisions`, which are tenant collections. It does not protect these.

What holds instead is that **no console-reachable accessor returns a
`reviewerId`, an assignment, or a per-juror vote**, and the forbidden-field list
names juror identity explicitly so a rename cannot quietly drop it. A
group-by-reviewer aggregation would be one field away from naming somebody; a
count cannot name anybody whatever is added to it.

The full analysis — including why this is the weakest protection in the system
and what becomes load-bearing the moment a privileged module reads these
collections — is [threat model §5](../architecture/threat-model.md). Read it
before writing the query, not after.
